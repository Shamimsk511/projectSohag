## Phase 2: Accounts
- [x] Account open/close (saving, loan), contract_amount, account_adjustments with reason
  - Plan: `AccountType` saving/loan only (investment/other when needed). `accounts`: party_id, account_number unique, account_type, contract_amount BIGINT null (required >0 for loan, null for saving), opened_at date (<= today), closed_at date null (null = active, no status column), closed_by, close_reason, created_by. Numbers SV-000001 / LN-000001 per type from `sequences` (key, value; `SequenceService::next()` insertOrIgnore + lockForUpdate inside caller's DB transaction; reused later for receipts). `account_adjustments`: account_id, old_amount, new_amount, reason, created_by; every contract change goes through it (stricter than "after collection", no silent edits ever). `transactions` table created now with full ARCHITECTURE schema (no writer until Phase 3; schedule_id plain column, FK with schedules) so `LedgerService` computes saving balance (deposits - withdrawals) and loan received/outstanding (contract - collections), excluding reversed rows and reversal rows. Close: balance/outstanding must be 0, else needs `limits.override` (admin) + reason. Inactive party cannot open accounts. Multiple accounts per type allowed. `AccountPolicy`: view = can view party; open/adjust/close = `accounts.manage`. UI: accounts card on party show, open form `admin/parties/{party}/accounts/create`, account show page with received/outstanding, adjust form, close form, adjustment history. Amount input via `TakaAmount` rule + `Money::fromTaka`. Non-goals: accounts list page, statement (next item), schedules/installment amount (Phase 4).
- [x] Account statement view (ledger-driven)
  - Plan: `LedgerService::statement($account, ?from, ?to)` returns `App\Support\AccountStatement` (opening, lines, closing) of `StatementLine` (transaction, in, out, running, reversed flag). Rows: saving = deposit (in) / withdrawal (out), running = balance; loan = collection (in) / disbursement (out), running = total received (disbursement shown, not counted, same as LedgerService). Reversals listed on their own date in the original's column as a negative amount; the original stays, flagged "reversed". Other types (adjustment etc.) omitted until Phase 3 gives them a direction. Whole account history loaded and walked in PHP (per-account volume is small, portable SQL); opening = running before `from`, closing over full history equals LedgerService figure. GET `admin/accounts/{account}/statement?from=&to=` (`AccountStatementRequest`: optional Y-m-d dates, to >= from, authorize = view account). Page: native date filter, table with neutral column labels per type, link from account show. Non-goals: export/print (Phase 6), pagination, party-wide statement.

## Phase 4: Collections

Weekly = weekday of starts_on; monthly = day of starts_on clamped to month end. `holidays` (date unique, name) admin page add/remove (`schedules.manage`, new permission, manager). Holiday: daily skipped; weekly/monthly shifted to next non-holiday date. `collection_schedules` (account_id, party_id, field_officer_id null, due_date, expected_amount, status `ScheduleStatus` pending/partially_paid/paid/missed/cancelled, notes, timestamps; unique (account_id, due_date); index (field_officer_id, due_date, status)); FK on `transactions.schedule_id`. `CollectionService::savePlan()` (create/update, audited, then generates today + tomorrow) / `generateFor(date)` (active account, plan in range, loan outstanding > 0, expected = min(installment, outstanding) for loans; existing row skipped; audit `schedule.generated` actor null). ## Phase 5.5: Hardening
- [x] Domain invariant test suite (ledger never edited, balances always rebuildable from transactions, no interest fields anywhere, every financial write has an audit row)
  - Plan: one `tests/Feature/DomainInvariantsTest.php`, no app changes unless a test exposes a bug. Static guards over source (app, database, routes, resources/views, resources/js, lang/{en,bn}/app.php, config/adminlte.php): no interest/profit/সুদ/মুনাফা/"Shariah compliant" wording; ledger rows created only in TransactionService; no query-builder update/delete/insert on immutable tables (transactions, audit_logs, cash_handovers, daily_closings) that would bypass the model guards. Schema guards: no interest/profit columns in any table, no stored balance/outstanding/received columns, every money column an integer. Behaviour: a scripted mix through the services (deposits, withdrawal, disbursement, scheduled collections, office entries, reversals, override) then every LedgerService figure (saving balance, loan received/outstanding, statement closing, office totals, schedule collected, cash in hand) equals an independent sum over raw `transactions` rows; every row amount > 0; every ledger row has exactly one audit row; reversal pairs reference each other once. Existing per-feature tests (model immutability, cash/closing/adjustment audits) are not duplicated.
- [x] Permission matrix tests (every route x every role, field officer cross-officer access denied)
  - Plan: `tests/Feature/PermissionMatrixTest.php`. One `MATRIX` const: route name -> roles allowed besides admin (admin passes everything via Gate::before + role middleware), built from `Permission::roles()`. Coverage guard: every named app route is in `MATRIX` or `OPEN` (home, login, logout, password.*, field.offline), so a new route fails until its access is decided. Per role (data provider, fresh DB): call each route with fixtures owned by ANOTHER field officer and an empty payload; allowed = not 401/403 and not sent to login, denied = 403 (FormRequest/policy authorize runs before validation). Guests: every matrix route redirects to login (401 for the JSON sync endpoint). Field officer gets 403 on another officer's schedule collect/store and receipt. No app changes unless a mismatch is a real hole.
- [x] Timezone/date-boundary tests (Dhaka midnight vs UTC, month-end receipts, closed day edges, SQLite vs MySQL date storage)
