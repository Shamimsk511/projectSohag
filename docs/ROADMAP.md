## Phase 1: Foundation

  - Plan: users += `phone` (nullable unique, BD 01XXXXXXXXX), `status` (`UserStatus` active/inactive). No delete (future ledger FKs): deactivate. One role per user. `UserService` create/update (role sync in DB transaction), `UserPolicy` via `users.manage`, Form Requests (admin cannot demote/deactivate self). Global web middleware signs out inactive users; login rejects them. Plain Bootstrap table + pagination (staff list is small). Menu item via BuildingMenu (translated). `app:create-admin` command for the first admin.
- [x] Parties CRUD, search, photo upload (FilePond), DataTable list
  - Plan: `areas` (name unique, status) + admin CRUD (plain table, like users). `parties`: party_code `P-00001` (from id, set inside create transaction), required name/phone/address/area_id; optional father_or_husband_name, mother_name, date_of_birth, gender, national_id (nullable unique), photo_path, nominee_name/relation/phone/national_id; status (`PartyStatus`). No party_type (derived from accounts later). No delete (deactivate). Phone not unique, BD format + Bengali digits normalised. `PartyPolicy`/`AreaPolicy`: view = `parties.view_all` or `parties.manage`, write = `parties.manage`; field officers no /admin party access. `PartyService` create/update (code, photo swap, old file deleted after commit). Photo: `intervention/image` ^3 (GD; prod needs ext-gd), scale down to 800px, re-encode JPEG q80 (strips EXIF), private disk `parties/`, streamed by `admin.parties.photo` after policy check. FilePond process/revert endpoint stores temp in `private/tmp/` keyed to session; form submits token. List: DataTables server-side via hand-written JSON endpoint + `PartyTableQuery` (search code/name/phone/NID, filter area/status, whitelisted order). Page JS `resources/js/admin/parties.js` (DataTables bs5, Select2, FilePond) loaded only on party pages. Show page: profile + nominee, placeholders for accounts/assignment. Non-goals: assignment, accounts, import, delete, NID scans.
- [x] Party assignment + reassignment with history
  - Plan: `party_assignments` (party_id, field_officer_id, assigned_from date, assigned_until date null, assigned_by, ended_by null, timestamps). Active = `assigned_until` null (no separate status column: one source). Dates are Dhaka business dates (`today(display_timezone)`). `AssignmentService` assign (locks party row, closes current with until=today, opens new; same officer rejected) / end. Only active users with field_officer role; inactive parties cannot be assigned (can be ended). `PartyPolicy::assign` = `parties.assign`; `view` also true for the party's currently assigned officer; `Party::scopeAssignedTo($officer)` for field queries later. UI on party show page: current officer + since, Select2 picker, end button (SweetAlert2 confirm), history list. Non-goals: bulk reassign (Phase 4 day lists), officer column/filter in party list, audit log (Phase 3).

## Phase 2: Accounts
- [x] Account open/close (saving, loan), contract_amount, account_adjustments with reason
  - Plan: `AccountType` saving/loan only (investment/other when needed). `accounts`: party_id, account_number unique, account_type, contract_amount BIGINT null (required >0 for loan, null for saving), opened_at date (<= today), closed_at date null (null = active, no status column), closed_by, close_reason, created_by. Numbers SV-000001 / LN-000001 per type from `sequences` (key, value; `SequenceService::next()` insertOrIgnore + lockForUpdate inside caller's DB transaction; reused later for receipts). `account_adjustments`: account_id, old_amount, new_amount, reason, created_by; every contract change goes through it (stricter than "after collection", no silent edits ever). `transactions` table created now with full ARCHITECTURE schema (no writer until Phase 3; schedule_id plain column, FK with schedules) so `LedgerService` computes saving balance (deposits - withdrawals) and loan received/outstanding (contract - collections), excluding reversed rows and reversal rows. Close: balance/outstanding must be 0, else needs `limits.override` (admin) + reason. Inactive party cannot open accounts. Multiple accounts per type allowed. `AccountPolicy`: view = can view party; open/adjust/close = `accounts.manage`. UI: accounts card on party show, open form `admin/parties/{party}/accounts/create`, account show page with received/outstanding, adjust form, close form, adjustment history. Amount input via `TakaAmount` rule + `Money::fromTaka`. Non-goals: accounts list page, statement (next item), schedules/installment amount (Phase 4).
- [x] Account statement view (ledger-driven)
  - Plan: `LedgerService::statement($account, ?from, ?to)` returns `App\Support\AccountStatement` (opening, lines, closing) of `StatementLine` (transaction, in, out, running, reversed flag). Rows: saving = deposit (in) / withdrawal (out), running = balance; loan = collection (in) / disbursement (out), running = total received (disbursement shown, not counted, same as LedgerService). Reversals listed on their own date in the original's column as a negative amount; the original stays, flagged "reversed". Other types (adjustment etc.) omitted until Phase 3 gives them a direction. Whole account history loaded and walked in PHP (per-account volume is small, portable SQL); opening = running before `from`, closing over full history equals LedgerService figure. GET `admin/accounts/{account}/statement?from=&to=` (`AccountStatementRequest`: optional Y-m-d dates, to >= from, authorize = view account). Page: native date filter, table with neutral column labels per type, link from account show. Non-goals: export/print (Phase 6), pagination, party-wide statement.

## Phase 3: Ledger core
- [x] `TransactionService` (record, reverse) with all DOMAIN_RULES + tests
  - Plan: `record(TransactionData, User $actor)` with `App\Support\TransactionData` (final readonly: type, amount, date, ?account, paymentMethod, ?reference, ?description, ?clientUuid, ?fieldOfficer, ?overrideReason); `reverse(Transaction, string $reason, User $actor)`. Rule failures throw `ValidationException`. Type/account match: loan_* -> loan account, saving_* -> saving account, office_* -> no account; investment_*/adjustment rejected (unsupported until designed). Amount > 0, date <= Dhaka today and >= account opened_at, account active. Withdrawal <= saving balance. Collection > outstanding needs `limits.override` + reason (`approved_by` = actor, new nullable `override_reason` column). Duplicate `client_uuid` returns existing row (`wasRecentlyCreated` false; unique-violation race re-fetched). Receipt `R-YYYYMM-00001` (`SequenceService 'receipt.YYYYMM'`, transaction month) for loan_collection/saving_deposit. party_id from account. DB transaction + account `lockForUpdate`. Reverse: `transactions.reverse` + non-empty reason (stored as reversal `description`), not a reversal, not already reversed, account active, reversing a deposit may not drive saving balance < 0; copies account/party/officer/schedule/amount, date today, no receipt. `PaymentMethod` enum cash/bank/mobile_banking (default cash). Non-goals: per-type role policy (screens item), officer-owns-party (sync endpoint), schedule status + locked day (Phase 4), audit (next item).
- [x] Audit log writer
  - Plan: `audit_logs` (user_id null = system/CLI, action string, auditable morphs, before/after json null, ip, user_agent(500), created_at only). `AuditLog` model immutable like `Transaction`. `AuditLogger` service: `created($action, $model, ?$actor)` (after = raw attributes) and `updated($action, $model, ?$actor, $extraBefore, $extraAfter)` (before/after = only changed columns, from `getPrevious()`/`getChanges()`, `updated_at` dropped); raw DB values (poisha ints, not formatted), model `$hidden` (password, remember_token) never stored; ip/user agent from current request. Called explicitly inside each writer's DB transaction with semantic actions: transaction.recorded/reversed, account.opened/contract_adjusted/closed, assignment.assigned/ended, party.created/updated, user.created/updated (role in before/after), area.created/updated. PartyService/UserService gain `?User $actor`; area writes stay in AreaController (wrapped in DB transaction). No-ops (duplicate client_uuid, same officer, failed rules) write nothing. Non-goals: audit viewer UI (Phase 6), login/logout events, pruning.
- [x] Disbursement, deposit, withdrawal screens (admin/accountant)
  - Plan: `AccountType::entryTypes()` (loan -> loan_disbursement; saving -> saving_deposit, saving_withdrawal) is the single list for screen + validation. `TransactionPolicy::create(User, Account)` = `ledger.post` + can view account; `reverse(User, Transaction)` = `transactions.reverse` + can view its account. `Admin\TransactionController`: POST `admin/accounts/{account}/transactions` (`StoreTransactionRequest`: type in entryTypes, amount `TakaAmount`, transaction_date Y-m-d, payment_method enum, reference <=100, description <=500) -> `TransactionService::record`, redirect to account with flash (receipt no when issued); POST `admin/transactions/{transaction}/reverse` (`ReverseTransactionRequest`: reason required <=500) -> `reverse`, back to statement. UI: "Post entry" card on account show (active + can create); statement rows get a Reverse button (can reverse, not a reversal, not reversed, account active) using `.js-confirm` extended with an optional Swal textarea that fills hidden `reason`. Non-goals: counter loan collection (Phase 4), printable receipt, override reason field.
- [x] Office income/expense
  - Plan: no schema change; `TransactionService::record` already takes office_income/office_expense with no account. `TransactionType::officeTypes()` list for screen + validation. `TransactionPolicy::viewOffice(User)` = `office_entries.post` or `reports.view_all`; `createOffice(User)` = `office_entries.post` (accountant; admin via Gate::before). `Admin\OfficeEntryController`: GET `admin/office-entries` (`OfficeEntryIndexRequest`: from/to Y-m-d, default current Dhaka month) lists office rows in period (date desc, paginated 50, eager `reversal` = new HasOne on Transaction) with reversed badge + reverse button (existing route, redirects back); totals income/expense/net for period from `LedgerService::officeTotals(from, to)` (excludes reversed rows + reversals). POST `admin/office-entries` (`StoreOfficeEntryRequest`: type in officeTypes, amount TakaAmount, date, payment_method, reference <=100, description required <=500 = what it was for) -> record, redirect to index. Menu item (can view). Page JS `resources/js/admin/office-entries.js` (confirm forms). Non-goals: categories/heads, export (Phase 6), cash balance report.

## Phase 4: Collections
- [x] Schedule generator (daily/weekly/monthly/custom) + scheduled commands
  - Plan: rolling generation from a per-account plan (officer read from the party's active assignment at generation time, so reassignment needs no row rewrites). `collection_plans` (account_id unique, frequency `PlanFrequency` daily/weekly/monthly, installment_amount BIGINT, weekdays json (daily only, 0=Sun..6=Sat, default all but Friday), starts_on (>= Dhaka today), ends_on null, created_by, timestamps). Weekly = weekday of starts_on; monthly = day of starts_on clamped to month end. `holidays` (date unique, name) admin page add/remove (`schedules.manage`, new permission, manager). Holiday: daily skipped; weekly/monthly shifted to next non-holiday date. `collection_schedules` (account_id, party_id, field_officer_id null, due_date, expected_amount, status `ScheduleStatus` pending/partially_paid/paid/missed/cancelled, notes, timestamps; unique (account_id, due_date); index (field_officer_id, due_date, status)); FK on `transactions.schedule_id`. `CollectionService::savePlan()` (create/update, audited, then generates today + tomorrow) / `generateFor(date)` (active account, plan in range, loan outstanding > 0, expected = min(installment, outstanding) for loans; existing row skipped; audit `schedule.generated` actor null). Command `schedules:generate {--date=}` (default tomorrow Dhaka) scheduled daily. UI: plan card + upcoming schedules on account show (`accounts.manage` to edit). Custom dates = manual rows in next item. Non-goals: missed marking, status from collections, editing rows.
- [x] Admin: view/edit schedules, reassign day lists
  - Plan: `CollectionSchedulePolicy` viewAny = `schedules.manage` or `reports.view_all`; create/update = `schedules.manage`. GET `admin/schedules` (`ScheduleIndexRequest`: date Y-m-d default Dhaka today, officer id or `none` = unassigned, status) plain paginated table (100) with count + expected total for the filter. `CollectionService` gains addSchedule (custom date: account active, date >= today, no row that date, officer from active assignment), updateSchedule (pending only: due_date >= today without clash, expected_amount > 0, notes), cancelSchedule (pending only, reason required -> notes), reassignDay(date, ?from officer, to officer) (moves that date's pending rows to another active field officer; temporary cover, party assignment unchanged). All lock rows + audit (schedule.added/updated/cancelled/reassigned). Screens: edit page `admin/schedules/{schedule}/edit` with cancel form (SweetAlert2 reason), add-date form on account show, reassign form on index when filtered by one officer. Non-goals: paid/partial changes (collections item), missed marking, multi-day bulk moves.
